# 设置项信息设计：说明文案的唯一去处是 ⓘ tooltip

状态：Accepted（2026-08，随「设置项 desc 收入 tooltip」PR 落地）

## 原则

**设置项的 label 行只有「名字 + 控件」，一切说明文字进 label 旁的 ⓘ tooltip。**

「说明」包括：这个参数干什么、默认值、推荐值、机制解释、代价与副作用。以前它们分两处——短的放 label 下的行内小字（`desc`），长的放 ⓘ tooltip（`helpTooltip`），同一字段常常两处各写一份。现在只有 tooltip 一处。

## 为什么

- **说明是「读一次即弃」的内容**。用户第一次配置时读一遍，之后每次打开设置页
  它都在占据版面、拉低扫读密度。设置页的高频动作是「找到某项、改值」，
  行内小字对这个动作只有噪音贡献。
- **两处说明必然漂移**。desc 与 help 各写一份，默认值改了往往只改一处
  （历史上多数 desc 的内容与 help 重复或已被 help 覆盖）。
- **一处收纳让 tooltip 成为完整答案**。用户点开 ⓘ 就该看到关于这个字段的
  全部信息，不需要再扫 label 下面还有没有补充。

## 结构性约束

`SettingsField`（`studio/web/src/pages/tools/settings/fields.tsx`）**有意不提供
行内 desc prop**——新增设置项写不出「标题下小字」，违反本原则需要先改组件，
改组件就会被 review 问到。这比约定靠得住（作者写时规范化：结构上做不出来，
而不是靠记得）。

## 边界（哪些不算「说明」、保留原状）

- **placeholder**：输入格式示例（如 `http://127.0.0.1:7890`）优先用
  placeholder 表达；tooltip 里可再带格式约束的完整说明。
- **控件旁的动态后缀**：如「0 = 关闭」「分钟」「已关闭：模型常驻直到手动清理」
  这类**跟随当前值变化**的状态提示是控件反馈，不是说明，保留在控件旁。
- **操作按钮组的上下文提示**：如安装/重装按钮组下方的一行注意事项，属于
  动作确认语境（用户即将点按钮时需要看见），不属于设置项说明。
- **section 标题下的段落引导**：section 级（非单个设置项）的引导文案按需保留，
  但同样警惕「读一次即弃」——能进 section 标题旁 ⓘ（`SettingsSection`
  的 `headerExtras` slot）就进。

## 适用范围

设置抽屉全部 tab（含 WandB 工作区、模型下载卡等子组件）。训练配置表单
（SchemaForm）的字段说明另有 schema `description` 管线，不在本文档范围，
但方向一致：说明跟字段走、集中一处。
