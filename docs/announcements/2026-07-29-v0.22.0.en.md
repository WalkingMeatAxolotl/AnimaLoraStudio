Evaluation gets its own page: one job per run, resumable, with a sample grid and much faster execution · faster image history on the Generate page

### Added

- **Evaluation has its own page, and one evaluation is one job (#469)**
  The project overview gains an "Evaluation" tab where you can browse past evaluations and start new ones. Evaluations no longer belong to a specific training run — once training finishes you can evaluate the checkpoints in the output folder anytime, as often as you like, and every run is kept so you can compare metrics before and after config changes.

  - A single evaluation used to flood the queue with hundreds of small jobs (one per checkpoint for images, plus one per metric); it is now one queue job with progress and logs in one place
  - The evaluation detail page has Overview / Metrics / Samples / Logs tabs; a training job's detail page also shows the evaluations triggered by that run
  - **Sample comparison grid**: the images generated for each checkpoint × validation image are laid out as a grid — zoom, pan, fullscreen paging, and PNG export included — so picking a checkpoint isn't just about staring at numbers
  - A canceled or failed evaluation can be **retried**; finished parts are not redone
  - New checkpoint sampling knob in the training config's evaluation settings: evaluate one, then skip N (default 0 = evaluate every saved checkpoint, same as before); the final weights are always included
  - After upgrading, the piles of task records left by the old evaluation model are cleaned up automatically: old metric results remain viewable, but the logs of those records are no longer kept

### Changed

- **The "none" attention backend option is now shown as "SDPA" (#472)**
  That option actually uses PyTorch's built-in SDPA attention — it never meant "disabled", and the old name was easy to misread. Display name only: saved configs and presets are unaffected, nothing to do.

### Improved

- **Evaluations run much faster (#470, #471)**
  The base model now loads once per evaluation, with LoRA weights hot-swapped between checkpoints (previously every checkpoint reloaded the base model — roughly 10 extra minutes across 21 checkpoints); metric models (CLIP / DINO / CCIP / WD14) also load once each. The more checkpoints, the bigger the win.
- **Image history on the Generate page loads much faster (#475)**
  Every visit used to rescan all saved images, which crept past a second once the folder grew (2000+ images); an index now makes listing about 14× faster. The history cap is also raised from 500 to 2000 entries, so older images are no longer cut off.

### Fixed

- **Accidentally starting a second Studio no longer loses your generated images (#473)**
  A second Studio instance would fail to start, but on its way out it deleted the running instance's image cache — new images vanished from the right-hand list and the preview kept saying the cache wasn't ready until a restart. Only one instance per data directory runs now; a latecomer exits before touching anything.
- **The LoRA picker on the Generate page no longer snaps back (#474)**
  Switching the project / version dropdowns in a slot that already held a LoRA would get reverted within a couple of seconds; it now stays where you put it.
- **LoKr / LoHa training logs are no longer flooded with dropout warnings (#468)**
  These algorithms don't support plain dropout yet (`lora_dropout` has no effect), and training used to print ~280 identical warning lines at startup; it is now a single line noting the parameter is inactive.
